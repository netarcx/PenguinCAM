# Pre-designed Tube Patterns

Read this before changing `tube_patterns.py`, `FRCPostProcessor.load_tube_pattern`, or the
tube branch of `/process`.

A tube job normally takes its pattern from a DXF. That is right when the pattern is
specific to the part, and needless work when it is the pattern every team puts in every
piece of 1x1 and 2x1: #10 clearance holes on half-inch centres, plus lightening where
there is room. `tube_patterns.py` generates that geometry directly, so a tube can be
machined **with no CAD step at all**.

---

## What gets generated

| | 1x1 (and 2x1 on its 1" face) | 2x1 on its 2" face |
|---|---|---|
| Hole rows | one, centred | two, 0.5" in from each long edge |
| Hole size | #10 clearance, 0.201" | #10 clearance, 0.201" |
| Pitch | 0.500" | 0.500" |
| Lightening | none — no room beside a centred row | right-triangle truss pockets between the rows |

The hole run is **centred on the tube length**, so both ends keep equal material and a
tube stays symmetric if it is later cut down. Holes never come closer than
`MIN_END_MARGIN` (0.375") to either end, where they would tear out rather than cut.

### Why triangles

The pockets are right triangles whose right angle alternates between the two sides of the
band from cell to cell. That leaves the remaining material running **diagonally** between
pockets — a zigzag web that carries load in tension and compression, rather than a
straight rail that carries it in bending. It is the same reason a truss is not a plank.

---

## The rules that keep it safe

Each of these drops geometry rather than emitting something the machine will mishandle:

- **A pocket the tool cannot clear is dropped.** The real constraint is the triangle's
  *inscribed circle*, not its area or its bounding box: a cutter wider than that cannot
  reach the corners, and the toolpath degenerates when offset inward. Checked against
  `POCKET_TOOL_CLEARANCE`, reported as a warning naming the tool.
- **`MIN_WEB` (0.125") of material is preserved** between every pocket edge and every hole
  edge, and between adjacent pockets. This is the web actually carrying load, so it is a
  floor, not a target.
- **A tube too short to hole safely gets no holes** and says so, instead of placing one
  where it will tear out.

All three are warnings, not errors — the program is still machinable without whatever was
dropped, and the operator is told what is missing.

---

## How it reaches the machine

Generated circles go through `classify_holes()`, the **same** door a DXF's circles go
through. That is deliberate: a pattern hole gets the same too-small-for-the-tool
rejection and the same peck-vs-helical decision as a drawn one, so there is no second code
path that could quietly disagree with the first.

No perimeter is invented. The tube face *is* the boundary, and the tube flow passes
`skip_perimeter=True`; a perimeter here would be a cut across the tube.

The pattern is symmetric about the face centreline, so the mirrored copy machined on face
2 lands on the same hole centres — a tube can be bolted from either side. This is why the
generated path never uses the two-face (distinct second pattern) mode.

## Using it

```bash
# 2x1, 24" long, holes + truss pockets, both faces, squared end
uv run python frc_cam_postprocessor.py --mode tube-pattern out.nc \
  --tube-pattern standard --tube-size 2x1-flat --tube-length 24 \
  --material aluminum_tube --thickness 0.0625 --tool-diameter 0.157 --square-end

# holes only
  ... --tube-pattern standard --tube-pattern-no-pockets
```

`--tube-size` sets both the face width and the tube height; `--tube-width` / `--tube-height`
override either when the extrusion is not standard. `--tube-length` is **required** with
`--tube-pattern`: it is what decides how many holes fit, and guessing it would hand the
operator a program for the wrong tube.

In the wizard: Setup → mode **Tubing** → Pattern → *Standard*. The tube length field
appears there, and the note under it gives the hole count before you generate anything.

## Verification, and what is NOT verified

`tests/test_tube_patterns.py` covers the geometry (spacing, centring, end margins, that
pockets never touch a hole or each other, that an oversized tool drops them), the
`load_tube_pattern` path, the `/process` route including the no-file case, and the G-code
formatting rules.

`gcode_audit.py` now audits tube programs too, via `audit_tube()`. **Only the
frame-independent checks run there** — comment rules, ATC/canned cycles, program end,
spindle restart after each flip pause. The ZMIN and rapid-below-top checks assume the
plate Z-frame, where material top is a fixed Z; a tube program works at
`Z = tube_height - wall` and pauses to flip rather than to change tools. **Physical-depth
auditing of tube programs is not covered.**

> **Nothing generated by this module has been cut on real stock.** See
> `MULTI_TOOL_STATUS.md` — well-formed, fully-passing, rule-compliant programs have been
> wrong here before. Dry-run above the work first.
